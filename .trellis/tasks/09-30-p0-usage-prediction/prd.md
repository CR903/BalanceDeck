# P0-2 用量预测与预计耗尽时间

## Goal

利用 scheduler 已采集的历史数据，按速率估算各窗口（5H / W / M）额度**预计耗尽时间**，在卡片 / 详情页展示，并明确标注「估算」，延续数据诚实原则。

## Background

- 竞品依据：Claude-God（burn rate 预测）、CodeZeno（runs-out estimate）、opencode-quota（runs-out estimate）均提供「按当前速率预计何时用完」。
- 对应调研报告 P0-2。
- 现有基建：`scheduler.ts` 统一频率采集调度，已有周期性采集数据的能力；详情页已有「每模型用量表」（官方口径）。

## Requirements

1. **本地历史快照**：scheduler 每次采集时，把各供应商各窗口的用量百分比 / 绝对量写入本地存储（JSON 文件或 SQLite，与现有存储方式一致），保留至少 30 天（保留期可配置）。
2. **速率估算**：基于最近 N 天（默认 7 天）快照计算平均消耗速率，估算「按当前速率预计在 `<时间>` 用完」。
3. **展示**：套餐类供应商在卡片环形仪表下方或详情页显示一行预计耗尽时间；余额类（无窗口概念）不显示。
4. **数据诚实**：预测文案必须标注「估算」；当数据源为 cached / local 时降低可信度或明确标注（如「基于缓存数据估算」）。
5. **隐私**：快照只存本机，不含密钥；不新增任何网络请求。
6. **测试**：估算纯函数（快照采样、线性斜率、时间预测、可信度降级）补充单元测试。

## Acceptance Criteria

- [ ] 每次采集后本地快照落盘，保留期默认 30 天且可配置
- [ ] 套餐类供应商在详情页（及卡片）显示预计耗尽时间；余额类不显示
- [ ] 预测文案含「估算」标注；数据源为 cached / local 时明确标注
- [ ] 估算纯函数有单元测试（覆盖：无历史数据、数据不足、速率为 0、窗口刚重置等边界）
- [ ] 无新增网络请求；`npm test` 全部通过
- [ ] `npm run typecheck` 通过

### 规划阶段（design.md）确认的实现决定与需求偏离

1. **AC2 收窄为「仅详情页」，不做卡片**：需求原文是「详情页（及卡片）」。设计收窄为**仅详情页** ——
   卡片空间紧张且折叠态常驻，预测文案会与余额数字争夺注意力。若后续要扩到卡片，需先确认布局能容纳。
   （design.md D6）
2. **不复用现有 `history.ts` 的 `HistoryPoint`**：它只存 `maxPercent`（不分窗口）、默认 cap=100
   （60s 间隔下仅约 100 分钟历史，比 7 天估算所需少两个数量级）。新建独立的分窗口快照存储，
   但**沿用**其纪律（缺失值保持 null、样本不足返回 null）。（design.md B1）
3. **快照不走 `extras`、独立落盘**：`store.ts` 的 `setExtra` 每次都全量重写整个文件，
   30 天分窗口快照走 extras 会造成每天数百 GB 的写盘。改为 `userData/usage-history.json` 按天分桶。
   （design.md B2）
4. **采样频率独立于采集频率，默认 15 分钟**：采集默认 60s，但消耗速率不需要秒级精度，
   沿用 60s 会让体积不可接受。（design.md B3）
5. **需求 1「与现有存储方式一致」按上述第 3 点调整**：仍在本机、不新增网络请求、不含密钥（AC4/AC5 不变），
   但落盘位置从 extras 改为独立文件 —— 这是在「与现有方式一致」与「不造成写盘灾难」之间的取舍，
   已在本 Notes 显式记录以便回看。
