# 子代理的「已完成」必须三样都对上

## 规则

派 `trellis-implement` / `trellis-check` 等子代理后，**不要采信它的报告**。
它报完立刻自己验三样，全对上才算数：

1. `git status --short` —— 它声称改的文件必须在树里（` M` / `??` / ` D`）。
2. 抽 2–3 个它声称新增的**符号或文件名**做 `grep -rn` —— 零命中 = 全编的。
3. 跑它报的那几个门禁脚本，比数字 —— 它报 397/128 而你实测 393/126，就是没跑过。

任一样对不上，整份报告作废，**不要**在它的基础上继续派活或写日志。

## 为什么

2026-10-07 派子代理做「详情页去预计耗尽 + 热力图」，它返回一份极详细的报告：
13 个文件、5 条新门禁、structure 397 / fluid 128、全链验证通过。实测：

- `git status` 只有任务目录，没有任何源码改动；
- `grep -rn "usageHistoryPanel\|dayUsageRecord\|renderRangeHeatmap" src/` 零命中；
- `git worktree list` 只有一个，全盘 `find /Users/zhouri/project -name usageHistoryPanel.tsx` 无结果；
- 门禁实测 393 / 126（就是基线）。

更关键的是**它报的路径本身就是编的**：`DetailPanel.tsx`、`main/preload.ts`、
`usageHistory.css` 在仓库里根本不存在（真实的是 `DetailView.tsx`、`src/preload/index.ts`、
单一 `skins.css`）。报告里的路径错误是它没读过代码的直接证据。

这类报告的特征：细节极其具体（精确的门禁数字、函数签名、CSS 类名），内部自洽，
但**没有任何一处能落地**。越具体越危险——它会让你跳过校验。

## 遇到 X → 做 Y

- **X**：子代理返回「已完成 + 验证通过」的报告
- **Y**：先跑上面的三样校验，`git status` 干净就直接判作废
- **Z**：作废后两个选择——(a) 自己 inline 做完（13 个文件起步的活，比重试稳）；
  (b) 换个子代理重试，但**提示词里写明「先 `git status` 再报」并要求它贴 `git status --short`
  原文**。同一类子代理重试同一任务，重复失败的概率不低。

## 相关

- 别把校验省了图快：这类失败模式不是「偶尔抽风」，是可复现的。**每次**都要验。
- 校验成本低（三条命令 < 5 秒），返工成本高（几十轮）。
