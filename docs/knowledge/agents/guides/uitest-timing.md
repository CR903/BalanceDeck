# uitest 断言必须「等条件成立」，不许「某一瞬间的 DOM」

## 规则

`--uitest` 的每一条断言，判据只能是**谓词**，不能是「睡固定值之后取一次样」：

1. **一个轮询实现**：`src/main/qa/uitest.ts` 的 `pollCheck(condJs, { mode, budgetMs, stepMs, diagJs })`
   是**唯一**的轮询原语；`pollAssert` / `waitIdle` / `waitCollectIdle` / `waitFor` / `dockWait`
   都是它的薄壳。第二套 `for` 循环迟早与第一套漂开（`waitFor` 曾经就是第二套）。
2. **负向断言用 `mode: 'absent'`，且谓词正向写**（断言「元素不在」就写「元素在」，等它不再成立）。
   两条路都要走通：出现过又消失 = 成立；**一直没出现 = 必须等满预算**才可判成立
   （「现在没看到」不等于「不会出现」）。
   ⚠ 预算判据必须落在**每一条路**上：只写在「一直没出现」那条分支里的话，条件恒真
   （该消失的东西一直没消失）时循环永不退出 —— 一条负向断言的**失败**会变成整轮挂死，
   比它想修的 flaky 更糟（`--uitest` 不设退出码，调用方一起卡住）。守卫：N8b。
3. **等采集用 `waitCollectIdle()`**（先等 `scanning` 为真、再等它为假），不许 `sleep(2500)`。
   一轮真实采集要出网，慢时超过 2.5s —— 那一轮会落在夹具注入**之后**把夹具冲掉。
4. **失败必须带现场**：默认 `diag` 抓「哪一屏 + 卡片数 + 皮肤 + 可见文案」，写成
   `fail:xxx | waited=…ms | diag=…`。只写 `fail` 的断言复现一次就得手工再跑一遍。
5. **稳定结构**（挂载即存在、且同段前面已经轮询确认过）写 `budgetMs: 0` —— 语义是
   「只取一次样，这里不需要等」，而不是绕过助手。

## 为什么

`--uitest` 是本仓唯一的运行期验收手段（无 linter、无 CI），它自己 flaky 等于每次验收都打折，
而且 flaky 的红会被当成「新引入的 bug」——前两个任务的核查代理都额外花时间用 `git archive`
另建 HEAD 基线去自证清白。实测（2026-10-18，`scripts/uitest-baseline.mjs`）：

- `intervalFlash` 约 **1/2** 概率红，且 HEAD 基线也红。成因**不是**「读早了」：临时探针实测
  `.saved-flash` 在动作后 **1–2ms** 就出现（`SettingsView.tsx:400-405`：`flash()` 置真、
  1600ms 后自灭），而旧写法是「`sleep(900)` 之后单点取一次样」—— `sleep(900)` 的**实际**
  耗时会被当时的负载拉长（同机轮间墙钟差可达 50s），取样点一旦越过 1600ms 的存活窗口，
  元素已经自灭 → `fail:no-flash`。所以**加长 sleep 只会更容易红**；只有「t=0 起轮询、命中即
  早退」两个方向都不会错过。
  ⚠ 这条结论本身被实测**推翻重写过一次**：原稿写的是「`await setExtras` 慢到 900ms 时 flash
  还没出现」，探针一跑就否掉了（它根本不慢）。**机制结论必须来自测量，不能来自听起来合理的猜测。**
- `grpUnknownBucket` 读到 `fail:{"at":null}`。成因：`setExtras({refreshInterval:'300'})`
  触发的那一轮真实采集慢过 `sleep(2500)`，落在 `debugPush(ghost)` 之后把注入的夹具冲掉。
- 「瞬时判据」共 **52 处**（`r.x = (await exec(…)) ? 'ok' : …` 同行 39 处 +
  换行写法 13 处）。⚠ **按行 grep 会漏掉换行写法**：取证时数出的 39 只是同行那一种，
  而两者是同一个缺陷。棘轮守卫因此按**归一化空白后的文本**计数。

## 遇到 X → 做 Y

- **X**：要断言「点击后某元素出现/某值落盘」→ **Y**：`await pollAssert(cond, 'label', { budgetMs })`，
  预算定在**实测等待时长的 2–3 倍**（把 `waited=` 写进 ok 串，让预算有依据）。
- **X**：要断言「移除/关闭后某元素不在」→ **Y**：谓词正向写 + `mode: 'absent'`。
- **X**：夹具段要等一轮真实采集收尾 → **Y**：`await waitCollectIdle()`（不是 `sleep(2500)`）。
- **X**：要等一个**复合**判据（在某个块里 + 无标签 + aria 不含某后缀）→ **Y**：整条谓词塞进
  `waitFor(...)` 一次等，不要「先等卡片出现、再单点读三个字段」。
- **X**：某个键始终红（放大预算也不出现）→ **Y**：那是**产品竞态**，记进「存疑」+ 给复现命令，
  **不要**用「重试到过为止」或「加大 sleep」换绿。
- **X**：要断言一个**只活一小会儿**的元素（`saved-flash` 这类 1.6s 自灭的 toast）→ **Y**：
  轮询必须**从动作那一刻（t=0）起**，不能等 `sleep` 之后 —— 一旦第一次取样晚于自灭时刻，
  **重试再多也等不到**（重试只能救「还没出现」，救不了「已经没了」）。并且要**先等上一动作
  留下的同类元素自灭**再派发（否则会读到残留、把「这次没闪」判成绿）；
  否则 Z：键会以「偶尔红」的形式长期存在，而它看起来像产品 bug。
- **X**：写一条 `mode: 'absent'` 的负向判据 → **Y**：确认预算判据在**每一条路**上都判
  （见规则 2 的 ⚠）；否则 Z：条件恒真时**整轮挂死**，比 flaky 更糟。

## 附：`--uitest` 的「整轮挂死」不是断言卡死，是进程不退

2026-10-18 定位（三次观测后）：**断言全部跑完、`"uitest": true` 的 JSON 已经写到 stdout，
但 `app.quit()` 之后进程不退出** —— `ps` 显示主进程 0% CPU 存活十分钟，GPU/渲染/网络/音频
四个 helper 全在，`sample` 显示主线程空转（等事件）。收到 SIGKILL 后进程才退，旧脚本的
`'close'` 处理器随即解析出了 171 键。

**后果**：任何「等进程退出再读结果」的调用方都会把「产品收尾问题」误读成「测试挂死」，
丢掉一整轮测量（用户先前手工基线就这么丢过一轮）。

**规则**：

1. 结果以 stdout 的 JSON 为准 —— **一出现就收下**，不等进程退出。
2. 收尾要杀**进程组**（`detached: true` + `process.kill(-pid, 'SIGKILL')`）：只杀主进程时
   helper 还活着、stdio 管道不关，`'close'` 永不触发。
3. 判「收尾卡住」要给**宽限窗口**（实测 300ms 会把正常收尾也标成异常；用 8s）。
4. 清理临时目录要**重试**：刚被整组杀掉的 helper 还在写，裸 `rmSync(recursive)` 会抛
   `ENOTEMPTY`（实测把整批跑崩）。

  每轮有墙钟上界，超时记成 `timeout` 而不是让测量卡死。
