# 本机大库扫描：WAL 活跃区不能当缓存键、JSON 列只能靠投影 + 增量

取证来源：2026-10-18 任务 `10-18-local-db-off-mainthread`
（`docs/daily/2026-10-18_local-db-off-mainthread.md` 有完整日志与真机输出）。
适用面：**任何「周期性读一个别人正在写的大文件/大库」**的代码
（本仓：`src/main/adapters/opencode-local.ts` / `opencode.ts`）。

## 遇到 X → 做 Y，否则 Z

### 1. 缓存键里带 `-wal`/`-shm`（或任何"活跃写入区"）→ 等于没有缓存

遇到：为了让缓存"及时失效"，把 WAL 模式下**每次写入都会动的那个文件**的 size/mtime 也拼进缓存键。

它会这样坏：opencode 活跃写入时 `opencode.db-wal` **5 秒内就变**（实测
`3221872@…401` → `3448472@…406`）。于是 120 秒的 TTL 永远等不到 —— 每一轮都是"缓存未命中"，
每一轮都在主进程同步重扫 651MB（实测 1.9–4.1s），用户看到的是鼠标转沙漏。

做 Y：缓存键只放**主库**的 `size:roundedMtime`（WAL 写入不落主库），
把"要不要干活"交给**变更探针**，把"数据新鲜不新鲜"交给**增量水位**：

```ts
// 变更探针（三者全等 ⇒ 0 次查询直接返回上次结果）
const dv = db.prepare('PRAGMA data_version').get()   // 另一个连接提交过就变
const mx = db.prepare('SELECT MAX(rowid) FROM t').get()  // b-tree 右端，实测 0.02ms
const stamp = mainDbStamp(dbPath)                     // 主库 size:roundedMtime
```

否则 Z：`-wal` 一变就全量重扫 ⇒ "缓存"只是把每轮 2 秒变成每轮 1.9 秒。

**关键实测**：`PRAGMA data_version` 恰好是那个正确的判据 ——
它对"另一个连接**真的提交了会改变读结果的东西**"敏感（INSERT / UPDATE / checkpoint 都会让它变），
而**文件被 touch（utimes）不会让它变**。所以它区分得了"真写了"与"只是被动过"，
而 `-wal` 的 mtime 区分不了（这正是它不能当判据的原因）。用法要点：
**同一个连接**上前后两次求值才有意义 ⇒ 连接要长期持有（本仓 `createLocalScanner` 的 `conn`）。

⚠ **边界（2026-10-18 核查代理实测）**：`data_version` **不会**被"无内容变化的写入"推动 ——
`UPDATE t SET time_updated = time_updated` 实测 `changes() = 1` 但 `data_version` 2→2；
把值真的 `+1` 才 2→3（SQLite 的 no-change 优化）。这对读方是**安全的**
（内容没变 ⇒ 投影也没变 ⇒ 没有东西要重读），但它给出一条纪律：
**判据不能是 `changes()` 或"写过几次"，只能是 `data_version`**；
也提醒"我先构造一个 no-op 写入来验证探针"这种测试会得到**假阴性**（核查第一轮就踩了）。

### 2. 要的数据只在 JSON 列里 → SQL 投影省 CPU，但省不掉页读取

遇到：整列 `SELECT data` 取回来在 JS 里 `JSON.parse` 出几个字段（本仓 2.6 万行 / 265MB / 2.6 万次 parse）。

它会这样坏：651MB 真库实测 **1935–4131ms/轮**（真机取证时负载不同），
其中 SQL 1112ms + JS parse 806ms，全部发生在主进程的同步路径上。

做 Y：SQL 侧 `json_extract` 投影 + 过滤，只把用到的 13 个字段取回来（0 次 `JSON.parse`）。
三条纪律：
- **`json_valid(data)` 必须有**：`json_extract` 遇到坏 JSON 会**抛错**，一行坏数据就让整轮扫描失败
  （旧实现是逐行 try/catch 容忍的，不能退步）。实测它不加成本（SQLite 的 JSON 解析结果有缓存）。
- **SQL 过滤写成"安全超集"**，判据的权威留在 JS 侧：只推入"JS 一定会拒"的条件
  （`IS NULL`、数值 `<= 0`）；TEXT 值在 sqlite 里恒大于数字，所以 `cost > 0` 只会**多**带行、
  不会少带 —— 方向必须永远偏向"多带"，否则口径就漂了。
- **别名即契约**：`json_extract(...) AS cost` 的别名就是 JS 侧字段名。

否则 Z：省下来的只是 CPU（实测 2.8–3.4×），**页读取量一分没省** ——
投影后仍是 ~650–820ms/轮，因为 SQLite 还是得把那 265MB 的 `data` 页读出来才能 `json_extract`。

**所以第二刀是必须的**：想进毫秒级只有两条路 ——
① **别扫 31 天**（增量：只重读最近写过的行，实测 29–35ms）；
② **别在主线程扫**（worker / utilityProcess，本任务 deferred，判据写在任务 design.md §6）。
只做①不做②在"冷启动"这一轮仍然要付页读取量（实测 676–818ms 热页 / 1.1–2.9s 冷页+高负载）。

### 3. 增量游标别选没有索引的列（`time_updated` 是陷阱）

遇到：以"最后更新时间"为水位做增量 —— `WHERE time_updated > :watermark`。

它会这样坏：`time_updated` **没有索引**（真库 `sqlite_master` 里只有
`time_created` 与 `(session_id, seq)` 两个索引），任何以它为条件的查询都退化成**全表扫描**
（实测 200–350ms/轮），比"有索引但范围大"更糟。

做 Y：用 **rowid**（b-tree 的原生键）做游标：`rowid > 上次表尾 - 回看窗口 AND rowid <= 本次表尾`。
实测 EXPLAIN 确认走 `SEARCH ... USING INTEGER PRIMARY KEY (rowid>? AND rowid<?)`。
再加一条纪律：**窗口是"范围"不是"最后 N 行"** —— 区间上界是本次表尾，
所以期间新插入的行**永远**在窗口里（间隔多久都不漏）；窗口只影响"老行的迟到回写"能不能被看见。

否则 Z：为了省内存写了个"增量"，每轮仍是全表扫，只是名字叫增量。

### 4. 增量的合并键必须是**行身份**，不是内容

遇到：用 `(time, cost)` 之类的**内容键**去重/合并增量结果（旧实现就是按 `t|cost` 去重两表并集）。

它会这样坏：`cost` 被改写时那个键就变了 —— 同一条消息在新键下落一次、旧键下还留着旧的，
**被算两遍**（实测变异：结果里同一时刻出现两条、总额虚高）。

做 Y：合并/清理都以**物理行身份**（rowid）为准，内容去重只在**派生结果**那一步做
（本仓 `derive()` 里的 `t|cost` 去重逐字保留旧口径，那是"两表取并集"的语义，不是行身份）。
另外：**按窗口清理**是必需的 —— 查询结果里没有的行就是被删了，不清就变成幽灵数据
（实测变异：删掉的行仍在结果里）。

否则 Z：数字悄悄变大/变小，界面看不出异常，也没有任何报错。

## 反例（同一个坑的变体，本轮顺手核过的）

- **别对着一个"查询计划副产品"去对齐口径**（2026-10-18 核查代理实测）。旧实现两条查询
  `SELECT data FROM session_message WHERE type='assistant' AND time_created > ?` 与
  `SELECT data FROM message WHERE time_created > ?` 拿到**不同的计划** —— 前者
  `SEARCH … USING INDEX session_message_time_created_idx`（按 `time_created` 升序返回），
  后者 `SCAN message`（按 rowid 返回）。没有 `ORDER BY` 时"先遇到哪一行"就随计划变，
  于是**同一个去重键在两表里的胜者规则都不一样**，"旧行为"根本没有单一答案。
  纪律：**先 `EXPLAIN QUERY PLAN` 看清楚旧顺序是什么**，再决定要不要对齐；
  若旧顺序依赖计划（没有 `ORDER BY`），就**选一个确定顺序并把边界写进注释**，
  而不是去追一个会随统计信息漂移的目标。本仓实测这种分歧在真库上 **0 组**（4248 个去重键里重复 0 个）。
- **"表尾行被删"与"VACUUM 重排 rowid"不可区分 ⇒ 宁可多扫一次**：`MAX(rowid)` 回退时一律全量重扫。
  代价是删表尾那次多 0.7s（真库 16 次/整库生命期），换来的是游标永远不会指向错行。
- **全量核对（TTL）不能设成 10 分钟一次**：它是一次 ~0.7s 的同步阻塞。
  把"每轮 2 秒"换成"每 10 分钟卡 0.7 秒"只是让症状变稀。本仓取 6 小时，
  并且**明确写出盲区**（远离表尾的迟到回写、远离表尾的删除）由它收口，而不是假装没有盲区。
- **同步 spawn 读 Keychain = 永久阻塞**：`execFileSync('security', …)` 一旦触发 macOS ACL
  授权弹窗，主进程就永远堵在那里（没有任何超时能救）。必须异步 + `timeout` + 结果缓存
  （连"被拒绝"也要缓存，否则用户拒一次、下一轮又弹）。同型：每轮递归 `readdirSync`+`statSync`
  → 目录 mtime 短路（缓存**条目**而不是最终文件列表，否则子目录里的新文件会被漏掉）。
- **数字必须带测量条件**：同一个冷启动全量在"热页 + load 4.4"下是 676ms，
  在"冷页 + load 17"下是 2858ms。测量顺序也会造假 —— APFS 克隆出来的副本页缓存是冷的，
  谁先跑谁替对方把 651MB 读进来（实测差 6–7 秒）。所以：**交替跑、报两轮、附 load average**。
