# 采集调度的看门狗：预算 + 轮次号失效 + 双保险超时

取证来源：2026-10-18 任务 `10-18-sync-collect-watchdog`（`docs/daily/2026-10/2026-10-18_sync-collect-watchdog.md`
有完整日志与真机输出）。适用面：**任何「有一个长期在跑的调度循环 + 面向第三方的 await」**的代码
（本仓：`src/main/scheduler.ts` / `collect-loop.ts` / `request.ts`）。

## 遇到 X → 做 Y，否则 Z

### 1. 有「正在跑」的一票否决布尔 → 必须同时有**时间预算**

遇到：`if (running) return; running = true; … finally { running = false }` 这种形态。

它会这样坏：`try` 里任一 await 永不 settle ⇒ `finally` 永不执行 ⇒ `running` 永远是 `true` ⇒
之后每一轮都在第一行静默返回。**没有任何报错**，只有「数据时间戳不再前进」。

做 Y：把每一轮整体放进一个有上界的等待里（本仓 `src/main/deadline.ts` 的 `withDeadline`），
超时即复位并把状态如实推出去（`scanning:false` + 一个超时时刻字段）。

否则 Z：用户看到「同步 3 小时不动、点刷新毫无反应」，**只有重启能恢复** —— 因为那个 `true`
在进程生命周期内不会被任何人改回来。

实现纪律两条：
- 超时**不 reject**（返回判决对象），调用方不需要 try/catch；但**预算内 reject 原样抛出**
  —— 把两者都压成「失败」会让「超时」与「真失败」不可区分，采集失败的原因就此丢失。
- 两个回调都要挂上：超时之后原 promise 仍会 settle，迟到的 reject 若无人接收会变成
  进程级 unhandled rejection —— 而这恰恰出现在**正常路径**上。

### 2. 只复位 `running` 不够 → 还要**轮次号（epoch）失效**

遇到：超时后「把标志位复位、让下一轮开始」的修法。

它会这样坏：旧轮**仍在后台跑**。它迟到回来时会带着自己的结果继续写快照/推送/托盘 ——
于是新旧两轮同时写状态，用户看到的数据在两个来源之间乱跳（比卡住更难查）。

做 Y：单调递增的轮次号 + 一个 `current(epoch)` 判据，轮体在**任何写入或推送之前**问一次；
超时那一刻循环就把该 epoch 作废。

否则 Z：看门狗把「永久卡死」降级成了「偶发数据错乱」。

护栏形状（`scripts/test-collect-loop.mjs`）：超时后放行那个挂起的轮次，断言它拿到的
`current(旧 epoch) === false`；并且**间隔给大**（10s）确保「没有新轮开始」时这条仍然成立
（否则这条断言会被「下一轮自然会改 epoch」救活，成为假护栏）。静态那道守卫断言闸门出现在
`lastSnapshots =` **之前**（顺序反了等于没有闸门）。

### 3. `AbortController` 只是其中一条路 → 必须有 race 兜底

遇到：`setTimeout(() => ctrl.abort(), ms)` 当作超时的全部手段。

它会这样坏：`abort` 只对**已经进入 fetch 状态机**的请求有效。卡在建连前阶段
（DNS / TCP connect）的请求实测不受约束 —— `lsof -p <pid>` 零 TCP 连接、`sample` 里线程
99.4% 采样陷在 `select()`，而请求永不返回。

做 Y：abort（让底层连接尽快被放弃）+ `Promise.race`（即使 abort 管不到也必须在 `timeoutMs`
量级内返回失败）。两者都要，不是二选一。

否则 Z：超时形同虚设，而且**连记账都反映不出**（`markNetResult(true)` 写在响应体读取之前）。

配套：加一个 `decided` 标志。判负之后迟到的成功不得再 `markNetResult(true)` —— 否则
`failStreak` 被一个**其实已经超时**的请求清零，离线判定被推翻，界面上的离线横幅闪一下又没了。

### 4. 两个来源各设一次定时器 → 换成**循环式**，而不是再加一个卫兵

遇到：`scheduleLoop()` 既被定时器自身 `.finally` 调用，又被 `refreshNow().finally` 调用，
每次进入都 `clearTimeout` + `setTimeout`。

它会这样坏：并发进入时先设的句柄失去引用，`stopScheduler()` 清不掉 ⇒ 句柄泄漏，进程退不干净。

做 Y：`while + await sleep(delay)`，句柄是**闭包局部量**（只有一个睡眠者）。

否则 Z：再加一个 `scheduling` 卫兵也能挡住，但那是与重入赛跑；循环式是**没有赛道**。

护栏：直接读进程活动句柄 —— `process.getActiveResourcesInfo().filter(r => r === 'Timeout')`，
空闲时恰好 1 个、`stop()` 后 0 个。这比「断言 stop 后没有新轮次」强，后者看不见泄漏的句柄。

### 5.5. 收尾回调里的一次异常 → 不能带走调度权

遇到：`onTimeout` / 收尾推送 / 日志这类「轮次之外」的回调直接调用，外面没有 try。

它会这样坏：`push` 会走 `getOverlay()?.webContents.send(...)`，webContents 已销毁时**会抛**
（渲染进程崩溃、窗口正在销毁而 `closed` 还没处理；`maybeWrite` 自己吞异常，所以这是 `push`
唯一会抛的口子）。异常一路冒到循环体末尾 ⇒ **循环退出 ⇒ 采集永久停摆**，症状与第 1 条
（预算缺失）逐字相同，只是触发概率更低、更难复现。

做 Y：把轮次的**记账**（epoch 自增 + 日志 + 回调）也包进 try/catch，异常只记日志。
该轮在 `runOneRound` 里已经复位过 `inFlight`，吞掉它是唯一正确的选择。

否则 Z：一次推送异常 = 这个进程以后再也不采集，而界面上没有任何东西异常。

护栏：`onTimeout` 注入一个会抛的实现，断言「循环仍在排新轮」+「有日志」。

### 6. `current(epoch)` 闸门只有在**同一个同步块**里才成立

遇到：「先问一次闸门，再写状态」的守卫，中间夹着 `await`。

它会这样坏：`await` 会让出控制权，超时正好落在检查通过之后、写入之前的那一刻 —— 判过 `true`
的轮次已经作废，却还是把结果写进去了（经典 TOCTOU）。时序极窄，行为测试很难稳定复现。

做 Y：闸门与写入之间**不许有 `await`**（本仓 `scheduler.ts` 的 `runRound` 两处闸门都是
同步块内的「判完即写」），并**用静态守卫钉住这个前提**（`test-collect-loop.mjs` C8f/C8h：
切片里不许出现 `await`）。变异验证：插一个 `await` ⇒ 只有这条断言变红。

否则 Z：R2「迟到结果被丢弃」这条保证只在纸面上成立，且红的是数据不是报错。

**顺带一个可测的事实**：不要靠「理论缝隙」猜时序 —— Node 在**同一 tick 的两个定时器回调之间
会排空微任务**（实测 `timerA → microA → timerB`）。所以 `resolve({ok:false})` 之后的
`epoch += 1` 一定先于旧轮的任何后续 continuation；而「旧轮先 resolve」等于该轮在预算内正常
收尾（`clearTimeout` + 先到先得 ⇒ `{ok:true}`）。用几毫秒级的探针跑几十组边界样本，比推演可靠。

### 5. 手动刷新必须**返回结果**，不能只 `Promise<void>`

遇到：`ipcMain.handle('ui:refresh', async () => { refreshNow() })` + `Promise<void>`。

它会这样坏：渲染层无法区分「开始了」与「被丢弃」。「刷新被静默丢弃」是真实发生过的症状
（早退发生在推 `scanning:true` 之前），而 UI 上**没有任何东西可依据**。

做 Y：返回 `'started' | 'queued'`；排队时**当场**推 `scanning:true`。

否则 Z：用户说「点了没反应」，而日志里连一条被丢弃的记录都没有。

## 反例（同一个坑的变体，本轮顺手核过的）

- **缺失值不许填 0/近似值**：超时那一轮**不伪造数据** —— 快照沿用上一轮、时间戳如实继续变老，
  只多一个「本轮采集超时」的可选字段。给一个「刚刚刷新过」的假象比卡住更坏。
- **状态新鲜度用比较判，不要复制间隔**：渲染层判断「超时提示还要不要显示」用的是
  「超时时刻 **晚于** 最后一次成功同步时刻」，而不是「距现在小于一个采集间隔」——
  后者要把主进程侧的间隔设置复制到渲染层，两份必然漂。
