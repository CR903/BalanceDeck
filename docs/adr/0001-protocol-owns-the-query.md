# 协议是唯一决定「查哪个端点、怎么解析」的概念

内置预设与自定义实例都解析到同一个协议；协议是唯一决定端点与读取方式的东西。

背景：此前同一家供应商被实现两次 —— 内置预设走 `src/main/adapters/<vendor>.ts`，自定义实例走 `src/main/adapters/custom.ts`，两边按同一个协议 id（`deepseek` / `moonshot` / `zhipu` / `siliconflow` / `minimax`）分派，输出已经出现可见差异：DeepSeek 的赠送余额提示与 `is_available` 警告、401 的「官方 key / 中转站」提示、缺 key 时点名 `DEEPSEEK_API_KEY` 的提示，都只存在于其中一边。

决定：协议是唯一概念，允许两种实现形态 —— **协议声明**（端点事实 + 纯读取函数 + 自己的提示语）与**代码适配器**（请求签名、浏览器会话、本机文件等声明表达不了的情况）。两者注册在同一个协议名下，共用采集引擎的线上能力。协议 id 到实现的映射必须唯一。

## 落地后的边界（B1 收口时划定）

- **声明表 8 条**：`deepseek` / `moonshot` / `zhipu` / `siliconflow` / `siliconflow-intl` / `openrouter` / `openai-billing` / `generic`。内置预设实例与自定义实例走同一个工厂，解析结果必须一致（黄金样本 U 节逐条验证）。
- **代码适配器 7 条**：`opencode-go` / `claude-code` / `codex` / `copilot` / `qwen-bss` / `volc-billing`，以及 **`minimax`**。MiniMax 留在代码侧的原因具体而唯一：它的 Token Plan 失败后要回落旧平台端点（`/v1/query_balance`）并解读 `base_resp.status_code`，声明表达不了这条分支。**不要再提议把 MiniMax 声明化**，除非愿意放弃该回落。
- 设置页「添加自定义提供方」的目录 = 上述 8 条声明 + MiniMax（共 9 条），元数据与声明同源（只维护一张表）。
- `source`（数据来源标注）按**实例身份**推导：内置实例 = `官方接口`，自定义实例 = `自定义接口`；窗口内的说明文案（如「端点为社区验证版本」）按协议声明，两种实例一视同仁。
- 未配置凭据的提示按实例身份区分：内置实例点名环境变量（`envKey`），自定义实例给编辑指引 —— 因为环境变量是按预设 id 映射的，对自定义实例不存在。

## Considered Options

- **把响应读取做成声明式字段表 / 组合子**（`firstKey` / `difference` / `limit`）：可表达的形状不到一半 —— 实际存在 5 种读取形状（固定路径 + 币种 + 警告、固定路径 + 附加说明、宽容候选键搜索、算术或额度而非余额、双字段 + 平台状态码 + 备用端点），其余要靠逃生口，等于多维护一套 DSL。
- **让 probe 也变成函数，所有来源统一成协议**：此时采集引擎只剩「铸造 + 错误映射」，8 家 keyed 供应商「写一条声明即可接入」的杠杆消失；本机转录、sqlite、浏览器会话也会被硬塞进协议这个词里。
- **formal 两层注册表**（声明式 http 协议 / 代码协议，两种成员一等公民）：与最终方案行为一致，只是把区别显式命名；留待注册表真的需要区分时再说。
